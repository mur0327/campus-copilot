# 검색 개선 여정: RRF 융합, 어휘 갭 실패 분석, Best Bets

## 도메인

하이브리드 검색(의미 검색 + BM25)의 recall/MRR 개선 과정 기록입니다. 2026-07-04 ~ 07-05 세션에서
진행한 실험·구현·실패·롤백·최종 해법을 시간 순서로 담았습니다. 논문의 "검색 융합 방법"과
"커버리지·실패 유형 분석" 절의 기반 자료입니다.

## 출발점

이전 세션까지의 상태:

- 평가셋: 질문 20개(answerable 16 + insufficient 4), gold 문서 라벨링 완료
- 지표: **recall@5 0.8125, MRR 0.6875**
- 잔여 미스 3개: Q003(국가장학금), Q007(수강신청 기간), Q020(장학금 전화)
- 부검 도구로 미스 원인을 4유형(corpus_missing / pool_miss / merge_loss / ranked_low)으로
  분류할 수 있는 상태

부검 결과 잔여 미스 3개는 모두 **merge_loss** — 정답이 검색 후보 풀에는 있는데
병합에서 밀려나는 유형이었습니다.

## 1단계. RRF 융합 도입: 가중합의 구조적 약점 제거

### 문제

기존 병합은 가중합(semantic 0.7 + BM25 0.3)이었습니다. 이 방식은 "한쪽 검색에서만 강한"
정답에 구조적으로 불리합니다.

- Q007: 정답이 BM25 3위인데 semantic에 없음 → 0.3 가중치에 눌려 병합 탈락
- Q003: semantic 없음 + BM25 20위 → 같은 이유로 탈락
- Q020: semantic 10위 + BM25 없음 → 같은 이유로 탈락

### 가설과 사전 검증

RRF(Reciprocal Rank Fusion)는 점수가 아니라 **순위**로 융합합니다. 각 리스트에서
순위 r일 때 1/(k+r)을 부여해 합산하므로, 한쪽 리스트의 상위 히트가 다른 쪽 가중치에
눌리지 않습니다. k=60은 원논문(Cormack et al. 2009)의 표준 상수라 튜닝이 아닙니다.

구현 전에 오프라인 시뮬레이션으로 검증했습니다(운영 코드 무변경, 같은 후보 풀에
병합만 교체). 결과: recall 0.8125→0.9375, 회귀 0. k=10은 기존 통과 문항(Q019)을
후퇴시켜 배제했습니다.

### 설계 핵심: 랭킹 점수와 근거 관련도의 분리

단순히 병합만 바꾸면 안 되는 이유가 있었습니다. 근거(evidence) 필터가
`score >= 0.35` 문턱을 쓰는데, RRF 점수는 0.016~0.03이라 이 분기가 죽습니다.

"그냥 정규화하면 되지 않나"가 함정입니다. 정규화하면 어떤 질문이든 1위가 1.0이 되어,
**코퍼스에 답이 없는 질문에서도 근거가 항상 채워지고** LLM이 답을 지어내게 됩니다.
RRF는 랭킹 융합이라 "절대 관련도"를 의도적으로 버리는데, 근거 판정에는 절대 관련도가
필요합니다. 하나의 점수로 두 역할을 못 합니다.

해법을 실측으로 결정했습니다. "점수로만 통과(키워드 겹침 0인데 score≥0.35)"하는
근거가 실제로 있는지 20문항 전체를 조사한 결과 5건이 존재했고, 특히 Q017은 유일한
근거가 이 경로였습니다. 즉 문턱 조건을 없애면 근거가 비는 회귀가 실재했습니다.

따라서 **두 점수를 분리**했습니다:

- `score` = RRF: 랭킹 전용
- `relevance` = 기존 가중합 정규화 유사도: 근거 게이트 전용 (0.35 문턱 의미 그대로 보존)
- 의도 부스트는 두 점수에 같은 계수를 곱함(순위와 근거 채택에 일관 반영)

### 결과 (커밋 83ee798)

동일 풀 공정 비교: recall **0.75→0.875**, MRR **0.625→0.719**. Q003 미스→2위,
Q007 미스→1위, 회귀 0.

## 2단계. 측정 인프라 수정: 이중 임베딩 제거

평가 스크립트가 질문당 임베딩 API를 2회 호출(진단용 풀 조회 + 실제 검색 내부)하고
있었습니다. 호출이 2배라 rate-limit에 걸리기 쉽고, 실패가 조용히 삼켜져 **실행마다
recall이 0.8125↔0.875로 흔들리는** 원인이 됐습니다.

검색기가 내부에서 이미 계산한 병합 전 풀을 진단용으로 함께 반환하게 하고
(`include_pools` 플래그), 평가는 재검색 없이 그 풀을 읽게 바꿨습니다(커밋 52df337).

효과: 연속 실행이 완전히 동일한 숫자를 내게 됐고, 진단이 "검색이 실제로 본 풀"을
보고하게 되어 정확도도 올랐습니다. **측정이 흔들리면 이후 모든 실험 판단이 오염되므로,
개선 작업보다 측정 안정화가 먼저였습니다.**

## 3단계. Q020 해결: 어휘 갭과 쿼리 동의어

### 진단

Q020(장학금 문의 전화번호)의 정답인 교내전화번호부(CamPhNum)는 semantic 9위로 풀에
있는데 BM25에 전혀 안 잡혔습니다. 원인은 **어휘 불일치**: 문서는 "연락처", "장학"이라
쓰고 사용자는 "전화번호", "장학금"이라 묻습니다. BM25는 정확 토큰 매칭이라 연결이
안 됩니다.

RRF는 양쪽 리스트에 다 있는 문서에 유리하므로, 한쪽(BM25)이 비면 부스트로 밀어올리는
데 한계가 있었습니다(계수 2.4배가 필요했는데 이는 튜닝이라 배제).

### 해법 (커밋 dac4352)

- BM25 검색 시점에 고정 도메인 동의어로 질의 토큰을 확장: 전화번호→연락처·전화,
  장학금→장학
- 연락처 의도에서 정식 전화번호부(page_kind=contact)를 우연히 전화번호가 섞인
  문서보다 강하게 우대(1.2→1.4 차등)

결과: Q020 안정적으로 해결, **recall 0.9375, MRR 0.7812**. 잔여 미스는 Q018 하나.

## 4단계. Q018 실패 분석: 유기적 검색 레버 5단계 전멸

Q018("방학 기간은 어디서 확인하나요?")은 어휘 갭의 극단형입니다. 정답인 대학 공식
학사일정(www.honam.ac.kr/AcademicCalendar)에는 **"방학"이라는 단어가 한 번도 안
나옵니다**. 방학이 "하계/동계 계절학기", "개강일" 같은 날짜 라벨로만 표현되기
때문입니다. 그 결과 BM25는 토큰 매칭 0, 의미 검색은 top-60 밖입니다.

이 문제에 5가지 레버를 순서대로 시도했고 전부 실패했습니다. **각 실패의 원리**가
이 기록의 핵심입니다.

### 시도 1. 쿼리 동의어 (방학→계절학기·개강)

Q020과 같은 방식. 실패: "계절학기" 토큰을 **계절학기 전용 안내 페이지가 독식**합니다.
그 문서는 통째로 계절학기 얘기라 BM25 상위를 도배하고, 정작 달력은 계절학기를 12달 중
두어 줄만 언급해 점수가 낮습니다(문서 단위 38위). 동의어가 엉뚱한 문서만 밀어올렸습니다.

### 시도 2. LLM 문서 확장 (doc2query 계열)

문서마다 보조 LLM(gemini-3.1-flash-lite)이 "이 문서가 답하는데 본문에 없는 검색어"를
생성해 BM25 색인에 얹는 방식. Doc2Token(누락 토큰만 주입), Doc2Query--(환각 필터)의
교훈을 반영해 grounded 프롬프트 + 본문 중복 제거 + 다중 샘플 union으로 구현했습니다
(커밋 cf2e91f, 10fae92).

전 코퍼스 3,928개 문서에 백필까지 실행했으나:

- **확률적 비보장**: "방학"이 학과 미러 달력 55개에는 들어갔는데, 정작 정답 문서에는
  백필과 재생성 2연속으로 안 들어갔습니다. 스모크 테스트(3/3 성공)와 실제 실행의 차이는
  순전히 표본 운이었습니다. "나올 때까지 재생성"은 평가셋에 맞춘 선택 편향이라 중단했습니다.
- **전역 부작용**: 4천 문서에 키워드가 깔리자 BM25 점수 지형이 바뀌어 기존 통과 문항
  2개(Q003, Q007)가 한 칸씩 밀렸습니다. recall 유지, MRR 0.7812→0.7396.

**핵심 교훈: 확률적 생성은 품질 문제가 아니라 보장성 문제로 실패합니다.** "특정 문서에
특정 단어가 반드시 들어가야 한다"는 요구에 구조적으로 안 맞습니다.

데이터는 롤백하고(0.9375/0.7812 복원 확인), 코드는 기본 꺼짐 스위치
(`search_keyword_generation_enabled=False`) 뒤에 보존했습니다(커밋 8831187).
질문셋 확장 후 "안 본 질문에 대한 일반화 효과"를 재검증할 때 켤 수 있습니다.

### 시도 3. 결정적 클래스 라벨 (규칙 기반 주입)

LLM 대신 고정 규칙으로: page_kind=schedule(학사일정류) 문서의 색인에
"방학 여름방학 겨울방학 종강 개학"을 주입. 구현 전 시뮬레이션으로 검증했습니다.

- 전 청크 주입: **자기 IDF 파괴**. "방학"이 자연 상태 17개 청크에만 있는 희귀
  토큰이었는데 1,455개 청크에 주입하니 희소성이 무너져 라벨 매칭 점수가 무력해졌습니다
  (달력 722위).
- 문서당 1청크 주입(IDF 보존): 일정 클래스 전체가 top-10을 장악하는 데는 성공.
  그러나 정답 문서는 **같은 라벨을 단 55개 일정 문서(입시일정·편입일정·학과 미러)
  사이에서 16위**. 질의 "방학 기간 어디서 확인?"에는 클래스 안에서 어느 문서인지 가릴
  신호가 없어, 첫 청크 길이 같은 우연이 순서를 정했습니다.

**교훈: 클래스를 살리는 것과 클래스 안에서 대표를 뽑는 것은 다른 문제입니다.**

### 시도 4. 의도 부스트 확장

시기(deadline) 의도에 대표 사이트(general_academic) 소프트 우대(×1.1)를 확장하는
시뮬레이션. 효과 0. 이기려면 계수를 크게 키워야 하는데 그것은 특정 문서를 위한
튜닝이라 배제했습니다.

### 시도 5. 의미 검색 풀 확대

정답 달력이 semantic 20위 경계에서 깜빡이던 이력이 있어 풀 크기를 확인했으나,
**top-60에도 없음**. 7/2 재크롤(연도 창 롤오버)로 본문이 연도탭+날짜표만 남으면서
임베딩 자체가 "방학 기간" 질의에서 멀어진 상태였습니다. 경계 문제가 아니므로 풀
확대로는 해결 불가.

## 5단계. Best Bets: 검증된 미해결 질문에 대한 큐레이션 계층

### 근거

5단계 실측으로 "유기적 검색으로는 이 질문에서 이 문서를 보장할 수 없다"가
증명됐습니다. 남은 결정론적 수단은 큐레이션뿐입니다. Best Bets는 엔터프라이즈 검색의
표준 패턴(SharePoint, Funnelback, Optimizely 모두 내장)으로, 관리자가 정한
질문→문서 매핑을 검색 결과 최상단에 고정하는 방식입니다.

### 설계 (커밋 5bccfcf)

- **저장**: 코드 상수(매핑 1건뿐이므로). DB 테이블+관리자 화면은 실사용에서 필요가
  증명되면 승격.
- **매칭**: 단순 부분 문자열 트리거(방학·여름방학·겨울방학·종강·개학).
- **삽입**: 최종 결과 top-1에 고정, relevance 1.0(운영자가 관련성을 보증한다는
  큐레이션의 정의 자체이므로 근거 게이트 통과). 검색이 이미 찾았으면 승격만(중복 금지),
  문서가 DB에 없으면 조용히 스킵.
- **오탐 무해화**: 매칭을 복잡하게 만들어 오탐을 막는 대신, 오탐 비용을 "근거 슬롯
  1개 소비"로 제한. 예: "방학 중 도서관 운영시간" 질문이면 달력이 1위에 붙지만 도서관
  문서가 2위로 따라오고, LLM은 근거 4개 중 맞는 것으로 답합니다.
- **등록 원칙**: 검색이 못 푸는 게 **증명된** 질문만 등록(쓰레기장 방지). Q020은
  유기적으로 풀렸으므로 미등록.
- **평가 분리**: `retriever_best_bets_enabled` 설정 + 평가 스크립트 `--no-best-bets`
  옵션으로 순수 검색 품질을 계속 측정 가능.

### 결과

| 모드 | recall@5 | MRR | 미스 |
|---|---|---|---|
| 핀 포함(운영) | **1.0** | **0.8438** | 0 |
| 순수 검색 | 0.9375 | 0.7812 | Q018 |

MRR 증분(+0.0625)이 정확히 Q018 한 문항이 1위가 된 몫(1/16)과 일치 —
다른 질문에 대한 교란이 0임이 산술로 확인됩니다.

**보고 원칙: 두 숫자를 항상 병행합니다.** 핀 포함 숫자만 내면 큐레이션을 검색 품질로
포장하는 것이라 부정직합니다. "순수 검색 0.9375 + 큐레이션 계층 포함 1.0"으로 분리
보고합니다.

## 논문에 가져갈 포인트

1. **순위 융합(RRF)이 가중합보다 하이브리드 검색에 강건함**: "한쪽 리스트만 강한 정답"
   유형의 미스 3개 중 2개를 표준 상수(k=60)만으로 해결. 단, 랭킹 점수와 근거 관련도는
   분리해야 함(RRF 점수에는 절대 관련도가 없음).
2. **어휘 불일치(vocabulary mismatch)의 실증 분석**: 사용자 어휘와 문서 어휘의 갭은
   랭킹으로 못 고치는 recall 층의 문제. 쿼리 확장은 어휘가 문서에 "있으면" 통하고
   (Q020), "없으면" 엉뚱한 문서를 밀어올림(Q018).
3. **확률적 문서 확장의 보장성 한계**: LLM 키워드 생성은 코퍼스 전반 품질은 좋았으나
   특정 문서-특정 단어 보장이 안 되고, 전역 주입은 BM25 지형을 흔들어 기존 순위에
   부작용. 실패 원인이 품질이 아니라 보장성이라는 점이 기여.
4. **결정적 주입도 클래스 내 선택 문제는 못 풂**: IDF 보존 주입으로 문서 클래스를
   살려도, 질의에 클래스 내 변별 신호가 없으면 무작위적 요인이 순서를 결정.
5. **소량 큐레이션 계층의 정당화**: 유기적 레버 소진을 실측으로 증명한 뒤 도입하고,
   순수 검색 지표와 분리 보고. 좁은 도메인 키오스크에서 실용적 완결성을 얻는 방법.
6. **측정 인프라가 실험보다 먼저**: 평가 하네스의 이중 API 호출 같은 오염원을 제거해
   재현 가능한 숫자를 확보한 뒤에야 개선 실험의 판단이 유효해짐.

## 남은 과제

- 질문셋 확장(N=20은 작음) 후 전 지표 재검증. LLM 키워드 생성의 일반화 효과도 이때
  스위치를 켜고 재평가.
- 한국어 형태소 분석기(kiwipiepy 등) 검토: 복합어 분해(여름방학→여름+방학)로 BM25
  전반 개선 여지. 단 전역 변화라 확장된 질문셋 기준 전량 재검증과 함께. 단어 부재형
  갭은 분석기로도 안 풀림.
- Best Bets의 DB+관리자 화면 승격: 실사용에서 등록 수요가 증명되면.
