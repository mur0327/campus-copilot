# EXP-07 최종 응답 평가 프로토콜

이 문서는 qrel v4 발행 이후 현재 production 구성의 최종 응답을 평가하는 실행 계약이다.
판정 기준의 정본은 [../../eval/exp07-answer-rubric.md](../../eval/exp07-answer-rubric.md)다.

## 1. 목적

EXP-07은 현재 production 구성이 고정된 50문항에서 어떤 최종 응답을 만드는지 관찰한다.
성공률이 높아야 논문이 성립하는 합격 시험이 아니며, 검색 회수·근거 지지·배포 적합성·거절 행동이 어디에서 갈리는지 기술하는 최종 응답 평가다.

결과를 본 뒤 성공 기준을 바꾸지 않는다.
결과가 기존 서술과 다르면 결과에 맞춰 주장을 약화하거나 철회한다.

## 2. 입력과 구성

질문 입력은 [../../eval/questions.csv](../../eval/questions.csv)의 50문항이다.
기대 행동은 qrel v4 발행본의 `full_answer` 28건, `qualified_answer` 3건, `abstain` 19건이다.
Q011과 Q035는 동일한 질문이지만 각각 독립 실행·판정한다.

키오스크의 실제 채팅 요청과 같이 검색 `category`는 `null`로 둔다.
CSV의 카테고리는 결과 분석용 메타데이터로만 보존하고 검색 필터로 사용하지 않는다.

문항별 새 모범답안은 작성하지 않는다.
qrel v4의 질문 판정, 양성 페이지·evidence, `target_sources_v4.csv`와 동결 DB 청크에서 참조 묶음을 자동 생성한다.

## 3. 실행 범위

end-to-end 범위는 질문 입력부터 최종 구조화 응답까지다.

```text
질문
→ production hybrid 검색
→ evidence 필터
→ 운영 프롬프트와 LLM
→ JSON 검증·복구
→ 백엔드 후처리
→ 최종 ChatResponse와 표시 출처
```

브라우저 UI 자동 조작은 50문항 평가 범위에 포함하지 않는다.
최종 `ChatResponse`가 키오스크 컴포넌트에서 정상 표시되는지는 별도 스모크 테스트로 확인한다.

행동 블라인드 판정 화면은 최종 답변 본문과 표시 출처 카드를 재현하지만 `partial`·`insufficient` 상태 배지는 숨긴다.
이 배지는 사용자가 실제로 보는 요소이지만 모델의 `answerability`를 그대로 표현하므로, 실제 행동을 독립 판정하는 첫 단계에서 보여주면 목표 라벨을 직접 노출하게 된다.
따라서 이 화면은 픽셀 단위 UI 재현물이 아니라 독립 행동 판정을 위한 통제된 평가 화면이며, 상태 배지는 모든 사람 판정이 잠긴 뒤 진단 정보로 공개한다.

production 응답 캐시는 우회한다.
같은 질문의 두 번째 실행이 첫 응답을 재사용하면 반복 일치도 측정이 불가능하기 때문이다.
검색·필터·프롬프트·생성·후처리 코드는 현재 production 경로를 그대로 사용한다.

## 4. 사전 동결

실행 전 다음 항목을 커밋한다.

- answer rubric과 이 프로토콜
- 실행기와 판정 시트 생성기
- 마스킹·집계·manifest 도구
- 관련 테스트

실행 직전에 qrel v4 invariant를 다시 통과시킨다.
DB 문서·청크, Chroma ID 집합과 BM25 파일의 지문을 생성하고 세 바퀴 종료 후 같은 방식으로 다시 계산한다.
세 실행 중에는 크롤·파싱·재색인을 수행하지 않는다.

전후 지문이 다르면 해당 실행을 발행하지 않고 원인을 확인한다.
qrel 청크가 변경되거나 새 코퍼스가 평가 전제를 바꿨다면 qrel을 조용히 수정하지 않는다.

## 5. 반복 순서

고정 난수 시드로 50문항 순서를 한 번 섞고 같은 순서로 세 바퀴 실행한다.
첫 바퀴만 네 축의 본평가이며 두 번째와 세 번째 바퀴는 구조화된 답변 행동의 반복 일치도 진단이다.

세 바퀴는 같은 한국 날짜 안에 실행한다.
현재 날짜를 운영 프롬프트에 새로 주입하지 않으며, 실제 요청 시각을 시간 표현의 기준으로 기록한다.
날짜가 바뀌기 직전에는 예상 소요 시간과 RPM을 확인한 뒤 실행을 시작한다.

세 바퀴를 모두 생성한 뒤에도 첫 바퀴의 판정이 잠길 때까지 반복 결과를 판정자에게 보여주지 않는다.
반복 결과를 보고 첫 바퀴 점수를 바꾸지 않는다.

## 6. 요청 제한과 재시도

LLM과 embedding provider의 계정 RPM 상한은 실행 시 필수 인수로 받는다.
각 provider는 입력 상한의 80% 이하에서 실제 호출 시작 간격을 제한한다.
질문은 병렬화하지 않고 한 건씩 순차 실행한다.

최초 생성, JSON 복구와 provider 내부에서 관찰 가능한 재시도를 실제 호출 수에 포함한다.
`429`의 `Retry-After`를 확인할 수 있으면 다음 호출 가능 시각에 반영한다.
실제 호출 시각, 상태, JSON 복구 횟수와 실행 수준 재시도를 모두 기록한다.

동결된 Gemini SDK의 transport 재시도는 비활성 상태인지 실행기가 확인하며, 확인할 수 없으면 실행을 시작하지 않는다.
Voyage client의 자체 재시도는 0회로 고정하고 production `VoyageEmbedder`의 최대 2회 재시도는 유지한다.
`VoyageEmbedder`의 각 재시도는 같은 RPM limiter를 다시 통과하므로 실제 호출 시작 간격과 횟수에 포함된다.
SDK와 관련 패키지 버전은 실행 manifest에 기록한다.

내용이 나쁘거나 기권했다는 이유로 다시 생성하지 않는다.
정상 최종 응답이 없는 외부 서비스 오류에만 실행 수준 재시도를 최대 한 번 허용한다.
재시도 전 실패도 원본에 보존하고 첫 정상 production 응답을 사용한다.

최종 실패가 세 문항 연속 발생하면 실행을 `aborted`로 중단한다.
중단된 실행은 이어 붙이지 않고 새 실행 ID로 처음부터 다시 실행한다.

## 7. 원본과 manifest

마스킹되지 않은 원시 LLM 출력, 실제 주입 evidence와 최종 응답은 `eval/results/` 아래에만 보존하고 Git에 커밋하지 않는다.
원본은 접근이 제한된 로컬 파일로 두며 판정 전에 파일별 SHA-256을 생성한다.

판정 화면을 열기 전 다음 항목을 별도 커밋한다.

- 원본 파일의 SHA-256과 레코드 수
- 실행 Git 커밋과 qrel v4 manifest 해시
- 코퍼스·Chroma·BM25 전후 지문
- prompt hash와 model·provider 문자열
- production 설정값과 provider 기본 sampling 값 미지정 사실
- 요청 순서 시드, RPM 상한, 실행 시각과 API 호출 수
- 완료 또는 중단 상태와 오류 수

이 실행 동결 커밋은 pre-run 커밋에 amend하지 않는다.
동결 manifest가 없거나 원본 hash·50문항×3회·같은 날짜·코퍼스 전후 지문을 검증하지 못하면 판정 화면 생성기가 실행을 거부한다.

## 8. 사람 판정

첫 바퀴 50건은 단일 저자가 판정한다.
두 번째 독립 평가자는 필수 조건이 아니며 평가자 간 일치도를 주장하지 않는다.

첫 단계는 질문과 사용자 표시 최종 응답·출처만 보고 실제 행동을 판정한다.
두 번째 단계는 실제 주입 evidence와 라벨 없는 v4 참조 묶음을 보고 정확성·근거·배포 적합성을 판정한다.
모든 축이 잠긴 뒤에만 기대 행동과 모델 자체 판정, 파생 지표와 반복 결과를 공개한다.

첫·두 번째 단계는 하나의 비공개 본판정 HTML에서 순서대로 진행한다.
기대 행동, 모델 자체 판정, 원시 출력과 반복 응답은 이 HTML 파일 자체에 넣지 않는다.
전량 잠금 JSON을 검증한 뒤 별도의 비공개 공개·조정 HTML을 생성한다.
따라서 본판정 HTML 소스를 보더라도 세 번째 단계 정보가 먼저 노출되지 않는다.

애매한 문항은 축과 메모를 남겨 보류한다.
기대 라벨을 열지 않은 상태에서 보류 문항을 다시 검토하고, 모두 확정되기 전에는 결과를 발행하지 않는다.
공개 후 수정은 이전 값·수정값·이유·시각을 보존하는 조정 기록으로만 허용한다.

## 9. 개인정보

비공개 판정 화면에서는 최종 사용자 응답 원문을 보고 개인정보 위험을 먼저 판정한다.
판정 JSON은 개인정보 값을 복사하지 않고 구조화 라벨과 필요한 메모만 저장한다.

원시 출력에만 남고 최종 응답에서 제거된 개인정보는 사용자 대상 종합 성공과 분리한 내부 로그 위험으로 기록한다.
공유·커밋 가능한 산출물은 전화번호, 이메일, 주민등록번호, 학번과 토큰 등 개인 식별정보를 마스킹한다.

Git에는 세 실행의 마스킹된 최종 `ChatResponse`, 표시 출처 메타데이터, 판정·수정 이력과 집계 결과를 커밋한다.
원시 LLM 출력, 주입 evidence 전문, 요청 헤더와 비밀정보는 커밋하지 않는다.
본평가에서 `privacy_risk`로 판정된 문항은 세 회차 모두 공개 응답 본문과 evidence 메타데이터를 비공개 표식으로 대체한다.
원시 출력은 공개 산출물에 포함하지 않으며 민감 패턴이 감지된 건만 공개·조정 단계에서 별도의 내부 로그 위험으로 판정한다.

## 10. 결과

주 결과는 50문항의 엄격한 종합 성공과 행동·정확성·근거·배포 적합성별 건수다.
기대 행동별 결과, 과잉답변, 과잉거절과 불필요한 제한 답변을 함께 보고한다.

사용자 관점의 종합 성공은 50문항 전체를 분모로 하며 고립된 `system_error`를 실패에 포함한다.
답변이 있어야 판정 가능한 축은 실제 판정 가능한 분모와 제외 건수를 표시한다.

Q035를 제외한 49문항 결과를 같은 출력에서 다시 계산해 중복 민감도를 병기한다.
더 좋은 결과를 선택하지 않고 50문항 결과를 주 결과로 유지한다.

모든 비율은 `건수/분모 (비율)`로 쓴다.
질문셋은 목적 표집한 고정 셋이므로 신뢰구간·유의확률로 전체 학생 질문에 일반화하지 않는다.

## 11. 해석 계약

성공이 많으면 현재 구성에서 관찰된 안전한 응답을 보고하되 기존 실패 주장을 결과에 맞게 약화한다.
실패가 많으면 답변 품질이나 배포 준비도를 주장하지 않고 어느 단계에서 실패했는지를 분석한다.
성공과 실패가 섞이면 검색 회수·근거 지지·배포 적합성·최종 행동의 분리로 설명한다.

EXP-07의 절대 성공 건수는 논문의 합격 조건이 아니다.
결과를 본 뒤 기준을 완화하거나 기존 서사를 유지하는 것이 타당성 위협이다.
