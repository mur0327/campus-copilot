# Campus Copilot 문서 검색 성능 평가 — 2차 보고

작성일: 2026-07-05
(1차 보고: [evaluation-report.md](./evaluation-report.md), 2026-06-28)

## 1. 이번 보고의 요지

1차 보고(6/28) 시점의 검색 성능은 **Recall@5 0.44, MRR 0.34**였다.
그때 "정답을 못 찾는 원인"을 네 계층(파싱 품질 / 자료 커버리지 / 표현 어휘 차이 / 순위 경쟁)으로
분해하고, 계층별 개선을 다음 단계로 제시했다.

이번 보고는 그 개선을 실제로 수행하고 재측정한 결과다.

> **Recall@5 0.44 → 0.94, MRR 0.34 → 0.78** (순수 검색 기준)
> 여기에 소량의 큐레이션 계층을 더한 운영 기준으로는 **Recall@5 1.0, MRR 0.84**
> — 평가셋 20문항 중 정답이 존재하는 16문항 전부에서 정답 문서를 상위 5개 안에 찾는다.

같은 날 평가 질문을 50문항으로 확장한 결과, **순수 검색 0.94 / 0.78이 두 배 커진
질문셋에서도 유지됨**을 확인했다(7장 추기).

점수만큼 중요한 것은 과정이다. 이번 작업에서는 **시도한 방법이 실패한 경우에도 그 원인을
측정으로 규명하고 되돌렸으며**, 그 실패 분석 자체가 연구의 기여가 되도록 기록을 남겼다.

## 2. 평가 방법 (1차와 동일)

- 질문 20개(10개 영역 × 2문항), 정답이 코퍼스에 존재하는 16문항으로 채점
- 정답 기준(ground truth)은 검색 결과와 무관하게 사람이 독립적으로 라벨링
- 지표: Recall@5(정답이 상위 5개 안에 드는 비율), MRR(정답의 평균 순위, 1에 가까울수록 앞)
- 내용 기준 정답 판정(같은 문서가 여러 학과 사이트에 복제된 경우 포함)

1차와 달라진 점: 평가 스크립트가 질문당 외부 임베딩 API를 두 번 부르던 문제를 발견해
한 번으로 줄였다. 이전에는 API 호출 제한에 걸리면 **실행할 때마다 점수가 조금씩 달라지는**
오염이 있었는데, 수정 후 연속 실행이 완전히 같은 숫자를 낸다. 이후의 모든 수치는 이
안정화된 측정 기준이다.

| 단계 | 내용 | Recall@5 | MRR |
| --- | --- | --- | --- |
| 1차 보고 시점 | 의도 인식 순위 보정까지 | 0.44 | 0.34 |
| ① 코퍼스 정리 | 게시판 목록 페이지 제거, 옛 게시글 비활성화, 파싱 개선 반영 | 0.69 | 0.49 |
| ② 색인 품질 | 문서 제목·메뉴 경로를 검색 벡터에 포함, 게시글 감점, 문서 다양화 | 0.81 | 0.67 |
| ③ 순위 융합 교체 | 가중합 → RRF(순위 기반 융합) | 0.88 | 0.72 |
| ④ 어휘 다리 | 도메인 동의어로 질문-문서 어휘 차이 보완 | 0.94 | 0.78 |
| ⑤ 큐레이션 계층 | 검색이 못 푸는 것으로 증명된 1개 질문 유형에 공식 문서 고정 | **1.0** | **0.84** |

0.94 / 0.78이고, 운영(키오스크) 기준 성능이 1.0 / 0.84다.

1. ~~수집·파싱 파이프라인 단계 분리~~ → **완료.** 전체 재수집 없이 파싱·색인만 다시

2. ~~파싱 개선 반영 후 재측정~~ → **완료.** 위 표의 ①이 그 결과다.
3. 어휘 차이 대응 → **부분 완료**(아래 5장). 라벨 확장(20→50문항)은 남은 과제.

## 4. 주요 개선의 원리 (①~④)

### ① 코퍼스 정리 — 가장 큰 단일 개선 (+0.25)

검색이 못 찾는 주원인은 검색 알고리즘이 아니라 **코퍼스의 노이즈**였다. 내용 없는
게시판 목록 페이지 1,800여 개와, 연도 탭을 따라 무한정 수집된 과거 연도 달력·게시글
변형이 정답 문서를 밀어내고 있었다. 수집 규칙을 "최신 창"으로 재설계(게시판은 1페이지
상세만, 밀려난 옛 게시글은 비활성화)해 활성 문서를 7,534 → 3,928개로 줄이자,
학사일정 계열 4문항이 한꺼번에 풀렸다.

### ② 색인 품질 — 맥락 없는 조각의 문제 (+0.12)

문서를 조각(청크)으로 잘라 색인하면 각 조각이 "무엇에 대한 답인지"를 잃는다.
예컨대 졸업학점 표는 숫자만 남아 "졸업학점" 질문과 연결되지 않는다. 문서 제목과
메뉴 경로를 조각 앞에 붙여 색인하도록 바꾸자 이런 유형이 풀렸다. 또한 시한성
게시글(공지)을 제도 안내 페이지보다 약하게 감점하고, 최종 결과가 한 문서의 조각들로
도배되지 않게 문서당 1개로 다양화했다.

### ③ 순위 융합 교체 — 가중합의 구조적 약점 (+0.06)

본 시스템은 의미 검색(벡터)과 키워드 검색(BM25)을 함께 쓴다. 기존에는 두 점수를
7:3 가중합으로 합쳤는데, 이 방식은 **한쪽 검색에서만 강하게 잡힌 정답**에 불리하다
(예: 키워드 검색 3위인데 의미 검색에 없으면, 0.3 가중치에 눌려 최종 후보에서 탈락).

이를 RRF(Reciprocal Rank Fusion)로 교체했다. 점수 대신 **순위**로 융합하는 표준
기법으로, 상수도 원논문의 표준값(k=60)을 그대로 써서 우리 시험지에 맞춘 튜닝이 아니다.
교체 전에 오프라인 시뮬레이션으로 "개선 2문항, 회귀 0"을 확인하고 반영했다.

기술적 주의점 하나를 함께 해결했다: RRF 점수에는 "얼마나 관련 있는가"라는 절대적
의미가 없어서, 답변 근거를 고르는 문턱 판정에 그대로 쓰면 안 된다. 순위용 점수와
근거 판정용 관련도를 분리해 이 문제를 막았다.

### ④ 어휘 다리 — 질문의 말과 문서의 말이 다르다 (+0.06)

1차 보고에서 지적한 "표현 어휘 차이" 계층이다. 전화번호부 문서는 "연락처·장학"이라
쓰는데 사용자는 "전화번호·장학금"이라 묻는다. 단어가 정확히 겹쳐야 하는 키워드 검색은
이를 놓친다. 소수의 고정 동의어(전화번호→연락처 등)를 검색 시점에 보태는 것으로
해결했다.

## 5. 가장 어려웠던 문제: "방학" 질문과 실패 분석

마지막까지 안 풀린 1문항("방학 기간은 어디서 확인하나요?")은 어휘 차이의 극단형이다.
정답인 공식 학사일정 페이지에는 **"방학"이라는 단어가 아예 없다.** 방학이
"하계/동계 계절학기", "개강일" 같은 날짜 라벨로만 표현되기 때문이다. 단어가 없으니
키워드 검색이 잡을 수 없고, 의미 검색도 이 페이지(날짜 표 위주)를 "방학 기간" 질문과
가깝게 보지 않는다.

이 한 문항에 다섯 가지 방법을 순서대로 시도했고 **전부 실패했다.** 각 실패의 원인이
서로 달라서, 그 자체가 의미 있는 분석 결과다.

| 시도 | 결과 | 실패 원인 |
| --- | --- | --- |
| 1. 질문에 동의어 추가 (방학→계절학기) | 실패 | "계절학기" 단어를 계절학기 전용 안내 페이지가 독차지해, 정작 달력은 안 올라옴 |
| 2. AI로 문서에 예상 검색어 생성·주입 | 실패 | 생성이 확률적이라 **하필 정답 문서에만 "방학"이 안 들어감**. 게다가 전체 문서에 검색어를 깔자 잘 되던 질문 2개가 살짝 밀리는 부작용 → 되돌림 |
| 3. 규칙으로 일정 문서 전체에 "방학" 주입 | 실패 | 일정 문서 55개가 똑같이 올라와, 그 안에서 정답을 가릴 신호가 없음 |
| 4. 순위 보정 강화 | 실패 | 효과를 내려면 특정 문서를 위한 수치 조작 수준이 필요해 배제 |
| 5. 의미 검색 후보 확대 | 실패 | 정답이 후보 60위 밖 — 경계 문제가 아니었음 |

특히 시도 2는 시사점이 크다. AI가 생성한 검색어의 품질 자체는 좋았다(무작위 표본
검사에서 환각 없음). 실패의 원인은 품질이 아니라 **보장성**이다 — "특정 문서에 특정
단어가 반드시 들어가야 한다"는 요구를 확률적 생성은 구조적으로 만족시킬 수 없다.
"될 때까지 다시 생성"은 시험지에 맞춘 조작이므로 하지 않았고, 데이터를 되돌린 뒤
기능은 스위치 뒤에 보존했다(질문을 늘린 후 일반화 효과를 재검증할 예정).

### 해법: 큐레이션 계층 (Best Bets)

다섯 방법의 실패로 "일반 검색으로는 이 질문에서 이 문서를 보장할 수 없다"가 측정으로
증명됐다. 그래서 기업·기관 검색에서 표준으로 쓰는 **Best Bets**(관리자가 정한
질문→공식 문서 연결을 검색 결과 최상단에 고정)를 도입했다. SharePoint 등 상용
검색 제품이 모두 내장한 패턴이다.

- 등록 원칙: 검색이 못 푸는 것으로 **증명된** 질문만 등록한다. 현재 1건(방학 계열
  단어 → 공식 학사일정 페이지)뿐이다.
- 정직한 보고: 큐레이션은 검색 품질이 아니므로, 순수 검색 수치(0.94)와 큐레이션 포함
  수치(1.0)를 항상 나란히 보고한다. 평가 도구에도 큐레이션을 끄고 측정하는 옵션을 두었다.

## 6. 의의

1차 보고의 메시지("검색 성능의 상한은 자료 커버리지와 파싱 품질이 결정한다")를
이번 결과가 실증했다. 검색 알고리즘을 손대기 전에 코퍼스를 정리한 것(①)이 가장 큰
단일 개선이었고, 알고리즘 개선(③)은 그다음이었다.

추가로 이번 작업이 보탠 메시지는 다음과 같다.

> **좁은 도메인의 실서비스 RAG에서는 (1) 일반 검색의 개선 한계를 실패 실험으로
> 측정해 드러내고, (2) 그 경계 밖의 소수 질문을 큐레이션 계층으로 보완하되,
> (3) 두 성능을 분리 보고하는 것이 정직하고 실용적인 구성이다.**

## 7. 추기 (같은 날 오후): 질문 50문항 확장과 시드 확장

위 6장까지 작성한 직후, 남은 과제 1번(질문 확장)을 같은 날 수행했다. 결과를 추가한다.

### 7.1 질문 20 → 50문항 확장

키오스크 설문으로 받은 **실제 학생 질문 6개**(예비군, 졸업학점 확인, 자판기 등 —
우리가 만든 질문에 없던 날것의 어휘)를 포함해 30문항을 추가했다. 정답 라벨링은
검색 결과와 무관하게 전체 코퍼스에서 후보를 찾아 도메인 확인(사람)을 거쳤다.

**50문항 기준 결과: 정답 존재 32문항, 정답 부재(insufficient) 18문항.
순수 검색 Recall@5 0.94, MRR 0.78.** 새로 라벨된 질문 대부분을 검색이 즉시
찾았다 — 앞선 개선이 새 질문에도 일반화된다는 신호다.

### 7.2 정답 부재 18문항이 그려준 커버리지 지도

라벨링 과정에서 "왜 정답이 없는가"가 유형별로 정리됐다. 이것이 다음 커버리지
확장의 우선순위 지도가 된다.

| 유형 | 예 | 해결 경로 |
| --- | --- | --- |
| 별도 사이트 (크롤 범위 밖) | 도서관 운영시간, 기숙사 입사 | 크롤 시드 확장 |
| 로그인 벽 뒤의 대학규정 PDF | 예비군 출석 처리, 공결 규정 | 수동 1회 수집 + 로컬 주입 (계획됨) |
| 정적 페이지 자체가 없음 | 등록금 납부 안내, 학점 확인 위치 | 학과 공지에 그때그때만 게시 — 구조적 한계 |
| 수집 정책의 트레이드오프 | 장학 부서 상세(2월 공지) | "최신 게시글만 수집" 정책이 밀어냄 |

### 7.3 시드 확장 실험: 기숙사 사이트 추가

기숙사 사이트(dorm.honam.ac.kr)는 대학 홈페이지와 같은 시스템이라 크롤러가
그대로 작동해 58개 문서(입사 안내 포함)를 수집했다. 도서관은 별도 시스템이라
현 크롤러와 비호환임을 확인했다(향후 별도 대응).

여기서 중요한 발견이 나왔다. **문서를 수집했는데도 검색이 못 찾는다.**
"기숙사 입사 신청" 질문에 입사 안내 문서가 의미 검색 52위, 키워드 검색 60위
밖이다. 원인은 이 보고에서 반복된 어휘 문제의 세 번째 사례다: 학생은
"기숙사"라 하는데 문서는 "생활관"이라 쓰고, 본문의 "입사"는 전부
"입사안내·입사일·입사자" 같은 복합어여서 키워드 매칭이 안 된다.

> **커버리지 확보와 검색 도달은 별개의 층이다.** 문서를 모으는 것(수집)과
> 그 문서가 질문에 응답하게 만드는 것(검색)은 각각 따로 검증해야 한다.

이로써 형태소 분석 도입의 실증 근거가 세 건(방학, 교양필수, 입사) 쌓였다.

### 7.4 현재 종합 수치 (2026-07-05 저녁 기준)

| 기준 | 문항 | Recall@5 | MRR |
| --- | --- | --- | --- |
| 1차 보고(6/28, 20문항) | 16 | 0.44 | 0.34 |
| 2차 개선 후(20문항) | 16 | 0.94 | 0.78 |
| **50문항 확장 후(순수 검색)** | **32** | **0.94** | **0.78** |

미해결 2문항: 졸업 필수 과목(복합어 갭), 기숙사 입사(어휘+복합어 갭) —
둘 다 형태소 분석 도입으로 해결이 기대되는 유형이다.

## 8. 남은 과제

1. **한국어 형태소 분석 도입**: "여름방학↔방학, 교양필수↔필수, 입사일↔입사"처럼
   복합어를 못 쪼개는 것이 미해결 미스의 공통 원인으로 확인됐다(실증 3건). 검색
   전체가 바뀌는 변화라 50문항 전량 재검증과 함께 도입한다.
2. **대학규정 PDF 수집**: 로그인 벽 뒤의 규정 문서군을 수동 1회 수집해 로컬 주입
   경로로 색인한다. 정답 부재 18문항 중 여러 건이 해소될 것으로 예상되며,
   "문서군 추가가 정답 존재 비율을 얼마나 바꾸는가"의 전후 측정을 계획한다.
3. **답변 생성 품질 평가**: 지금까지는 검색 단계만 측정했다. 검색이 안정화됐으므로
   다음은 "찾은 문서로 얼마나 정확한 답을 만드는가"의 평가다.

## 9. 용어 사전 (1차 보고 사전에 추가되는 항목)

| 용어 | 뜻 |
| --- | --- |
| RRF (Reciprocal Rank Fusion) | 두 검색의 결과를 점수가 아니라 순위로 합치는 표준 기법. 각 목록에서 순위가 높을수록 큰 값을 부여해 합산한다. 한쪽 검색에서만 강한 정답도 살아남는 것이 장점. |
| 어휘 불일치 (vocabulary mismatch) | 사용자가 쓰는 단어와 문서에 적힌 단어가 달라 검색이 연결을 못 만드는 문제. 검색 분야의 고전적 난제. |
| 문서 확장 (document expansion) | 문서에 "이 문서가 답할 법한 검색어"를 미리 보태 색인하는 기법. AI 생성 방식(doc2query 계열)이 대표적. |
| 쿼리 확장 (query expansion) | 반대로 질문 쪽에 동의어·관련어를 보태는 기법. |
| Best Bets (큐레이션 고정 답변) | 특정 질문 유형에 관리자가 정한 공식 문서를 검색 결과 최상단에 고정하는 기능. 기업·기관 검색 제품의 표준 기능. |
| 형태소 분석 | 한국어 문장을 의미 단위(형태소)로 쪼개는 처리. "여름방학"→"여름"+"방학"처럼 복합어를 분해해 검색 매칭을 높일 수 있다. |
| 회귀 (regression) | 개선 작업이 기존에 잘 되던 것을 망가뜨리는 일. 본 작업은 매 단계에서 회귀 여부를 함께 검증했다. |
